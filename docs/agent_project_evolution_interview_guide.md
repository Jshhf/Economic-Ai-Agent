# Agent Project Evolution Interview Guide

## 1. 30 秒版本

这个项目不是一开始就做成平台的。最初它只是一个能跑通的 AI Agent 原型，支持上传 CSV、创建分析任务、双 Agent 生成报告并展示结果。后来我做了两次升级：第一次升级重点补了 Skill、RAG、MCP 和 Trace，把它从固定流程升级成可扩展、可观测的 Agent runtime；第二次升级我开始关注长任务里的上下文治理，补了 Goal Summary 这层，让系统能更稳定地表达整体目标、当前阶段和下一步动作。

## 2. 60 秒版本

我这个项目是分阶段演进出来的。最初版本比较简单，主要是 FastAPI 承接任务创建，上传 CSV 后用双 Agent 做分析和报告生成，再把任务状态和结果持久化到 SQLite 里，最后通过页面把报告展示出来。这个阶段主要解决的是“能不能跑通”。

后面我发现这个版本虽然能工作，但流程写得比较固定，而且中间过程不透明，所以第一次升级我重点做了 runtime 分层，把能力抽成 Skill、Tool、RAG、MCP 几层，同时把 agent run、tool call、source reference 和 metrics 都持久化下来，让系统具备可扩展和可观测能力。

再往下看，我又发现系统虽然已经能记录很多运行信息，但缺少一个稳定的任务主线对象，所以第二次升级我补了 Goal Summary 这一层，用来记录整体目标、当前阶段、关键发现和下一步动作，本质上是在补上下文治理能力。

## 3. 三阶段演进版讲法

### 阶段一：初版，先把链路跑通

初版的目标不是做平台，而是先把一条最小可用链路打通。

核心能力：

- FastAPI 任务创建与状态查询
- 上传 CSV
- 双 Agent 分析与报告生成
- SQLite 持久化任务状态和分析产物
- 页面展示结果

这一版解决的问题：

- 能不能从“上传数据”走到“生成结果”
- 能不能把 Agent 输出落成后端系统，而不是只停在 prompt demo

这一版的不足：

- 流程比较固定
- 场景比较单一
- 外部知识能力不够
- 中间运行过程不透明

### 阶段二：第一次升级，补扩展性和可观测性

第二版我没有继续往“多做几个页面”去走，而是先解决系统能力边界问题。

新增能力：

- Skill 抽象
- Tool / RAG / MCP 分层
- Source reference
- Trace
- Metrics
- Observability

这一版解决的问题：

- 初版流程写死，不够灵活
- 只能做一种任务
- 外部背景资料不足
- 结果出来了，但很难解释 agent 中间做了什么

这版的核心变化：

项目从一个“能出结果的 demo”，升级成一个“可扩展、可观测的 Agent runtime”。

### 阶段三：第二次升级，补上下文主线治理

第二次升级不是继续加更多工具，而是开始治理任务主线。

我观察到：

- 系统已经有 `EvidencePack`
- 有 `FollowUpRequest`
- 有 `FinalReport`
- 有 `Trace`

但这些对象记录的是运行结果和运行过程，不是稳定的任务主线。

所以第二次升级补了：

- Goal Summary
- 主线摘要持久化
- 按阶段更新的 context mainline
- 主线摘要注入 agent 输入

这一版解决的问题：

- 多阶段任务里目标不稳定
- 阶段信息分散
- 后续容易上下文膨胀
- 运行日志很多，但没有一个对象概括“我们现在做到哪了”

这版的核心变化：

项目从“能扩展、能观测”，继续升级成“上下文可治理”的 Agent runtime。

## 4. 高频问答

### 你为什么做第一次升级？

因为初版虽然能跑通，但流程比较固定，也不够透明。它更像一个单一任务 demo，缺少可扩展和可观测能力。所以第一次升级我重点做了 Skill 抽象、Tool/RAG/MCP 分层和 Trace，把它升级成可编排的 runtime。

### 你为什么做第二次升级？

因为第一次升级之后，系统已经能扩展也能观测，但我继续往下看时发现，系统缺少一个稳定的任务主线对象。它知道自己做过什么，却不够清楚当前整体目标、当前阶段和下一步动作。所以第二次升级我补的是 Goal Summary，本质上是在解决上下文治理问题。

### 你怎么判断出这些问题的？

我是从三个角度判断的。第一是现象层面，初版能跑通，但流程写死、任务单一，中间过程也不透明。第二是架构层面，第一次升级后已经有 trace、artifacts 和 source references，但没有一个专门记录长期任务主线的对象。第三是能力边界层面，我发现 RAG 能解决召回问题，但不能替代目标管理，所以我判断这是上下文治理问题，而不是单纯的模型问题。

### 为什么不能只靠 RAG？

因为 RAG 解决的是 retrieval，不是 task-goal management。它适合找回相关资料，但不能稳定表达当前目标、当前阶段、已完成步骤和下一步动作。对我这个项目来说，RAG 更像证据补充层，而 Goal Summary 才是任务主线层。

### Goal Summary 具体记录什么？

它固定记录整体目标、用户约束、输出要求、当前阶段、已完成步骤、已解决问题、未解决问题、关键发现和下一步动作。重点不是保存聊天历史，而是让 runtime 始终有一个稳定的任务主线对象。

### 现在这个项目还有哪些边界？

当前我只做到了主线摘要层，还没有继续做完整多轮聊天能力。比如 conversation memory、clarification policy、conversation RAG、resume/continue UI 这些都还没有做。这是一个有意收敛的工程取舍，因为我希望每次升级都针对一类核心问题，而不是一口气把所有概念堆进去。

## 5. “问题发现 -> 解决问题”的统一回答模板

你可以直接按这个模板答：

> 我这个项目不是一步到位做完的，而是我每做完一版，就会看这一版最明显的边界在哪里。初版的边界是流程固定、可观测性差，所以第一次升级我补了 Skill、RAG、MCP 和 Trace；第一次升级之后，系统已经能扩展、也能看到运行过程，但我发现它缺少一个稳定的任务主线对象，所以第二次升级我补了 Goal Summary。也就是说，我不是为了堆技术名词去升级，而是每次先观察系统问题，再决定下一版最值得补的能力。

## 6. 面试时一定要避免的说法

不要这样说：

- 一开始我就设计成了完整平台
- 一开始就有 RAG、Skill、MCP、Trace
- 后面只是微调了一下

更稳的说法是：

- 初版先解决能不能跑通
- 第一次升级解决可扩展和可观测
- 第二次升级解决任务主线和上下文治理

这样面试官更容易相信这是你真实做过、想明白过的工程演进过程。
