# Skill 渐进式披露设计文档

## 1. 设计目标

本设计希望解决一个 runtime 层面的治理问题：

在多阶段 Agent 任务中，不同阶段对能力的需求并不一样。如果一开始就把所有工具、所有 source 和所有上下文全部暴露给 Agent，会增加搜索空间，也会削弱阶段边界。

因此设计目标是：

- 让 Skill 不只描述“场景”
- 还描述“某个阶段应该披露哪些能力”

最终希望做到：

- 数据分析阶段先收敛
- 审查阶段先判断证据充分性
- follow-up 阶段才进行定向补证据
- writer 阶段专注写作和引用

---

## 2. 设计原则

### 2.1 先收敛，再扩展

默认优先暴露最小必要能力，而不是默认开放最大能力集合。

### 2.2 阶段边界清晰

每个阶段都要有明确职责：

- `data_analysis` 负责结构化证据生成
- `economist_review` 负责证据审查
- `economist_follow_up` 负责定向补证据
- `economist_writer` 负责最终写作

### 2.3 与现有 runtime 保持兼容

本次设计不重做整套运行时，而是在现有：

- `Skill`
- `phase`
- `FollowUpRequest`
- `Goal Summary`
- `Trace`

这些基础上增量增强。

### 2.4 能落到面试表达

设计不只是为了代码结构，也要能够支持面试里清楚解释：

- 为什么不同阶段不应该暴露同样的能力
- Skill 为什么不只是 prompt 模板
- runtime 是如何治理 Agent 行为边界的

---

## 3. 数据模型设计

### 3.1 `SkillDefinition`

新增字段：

- `stage_disclosures: dict[str, SkillStageDisclosure]`

### 3.2 `SkillStageDisclosure`

字段：

- `stage`
  - 当前阶段名

- `stage_goal`
  - 当前阶段的任务目标说明

- `allowed_tools`
  - 当前阶段允许暴露的数据工具

- `rag_enabled`
  - 当前阶段是否允许使用 RAG

- `mcp_sources`
  - 当前阶段允许访问的外部 source

- `output_type`
  - 当前阶段期望输出类型

- `disclosure_rationale`
  - 为什么这个阶段只披露这些能力

这个模型的作用是把“阶段目标”和“阶段能力边界”绑定在一起。

---

## 4. 运行时设计

### 4.1 阶段驱动能力装配

运行时不再只看 skill 的全局配置，而是看：

- 当前 `skill_id`
- 当前 `phase`

再由这两个维度共同决定：

- 可以用哪些数据工具
- 能不能用 RAG
- 能调用哪些外部 source

### 4.2 Agent 指令中显式注入披露块

给每个 Agent 指令增加 `Skill Disclosure` block，内容包括：

- 当前阶段
- 阶段目标
- 当前允许的工具
- 当前是否允许 RAG
- 当前允许的外部 source
- 当前输出目标
- 当前披露原因

这样做的目的不是让模型“自由发挥”，而是让 runtime 显式告诉模型：

- 现在处在什么阶段
- 现在应该用什么能力
- 现在不应该乱用什么能力

### 4.3 fallback 逻辑同步遵循阶段披露

这次设计不只约束 OpenAI 路径，也约束 fallback。

因此：

- fallback 拉取来源时也要根据当前阶段的披露配置决定是否拉 RAG
- fallback 访问外部 source 时也要读取当前阶段可用 source 列表

这样可以保证：

- 不同运行路径遵守同一套能力边界

---

## 5. 典型阶段设计

### 5.1 `data_analysis`

特点：

- 先聚焦数据本身
- 不引入外部知识噪声

披露策略：

- 开放结构化数据工具
- 关闭 RAG
- 不开放 MCP source

### 5.2 `economist_review`

特点：

- 不是重新算数据
- 而是判断证据是否充分

披露策略：

- 不开放原始数据工具
- 开启轻量 RAG
- 只开放有限外部 source

### 5.3 `economist_follow_up`

特点：

- 只在证据不足时触发
- 目的是补特定缺口

披露策略：

- 开放定向分析工具
- 允许更深一层外部来源
- 不重新回到“全量探索”

### 5.4 `economist_writer`

特点：

- 主要负责整合和写作

披露策略：

- 不暴露完整分析工具面
- 主要使用证据、主线摘要和来源

---

## 6. 与项目整体架构的关系

这个设计在项目里的定位如下：

- `Skill`
  - 负责场景定义与阶段能力披露

- `Goal Summary`
  - 负责任务主线治理

- `Trace / Observability`
  - 负责运行过程可观测

- `RAG`
  - 负责检索增强

- `MCP-style adapter`
  - 负责外部能力接入

所以这次升级不是替代已有模块，而是把它们组织得更清楚。

---

## 7. 为什么这套设计有价值

### 7.1 对模型更稳

一次性暴露全部能力，会让模型更容易发散。

按阶段披露以后，模型的动作空间更小，目标更聚焦。

### 7.2 对工程更清晰

不同阶段的职责边界更清楚，后续扩展：

- 新 skill
- 新 source
- 新阶段

都会更可控。

### 7.3 对面试更好讲

面试时可以清楚说明：

- Skill 不只是 prompt 模板
- runtime 不只是 prompt chaining
- 项目开始具有“能力治理”思路

---

## 8. 当前边界

这次设计仍然是工程上收敛后的版本，还没有继续做：

- 动态基于结果自动调整披露等级
- 更细粒度的 source 访问策略
- 基于 trace 反向优化披露策略
- conversation 级别的多轮披露控制

所以当前版本更准确的定位是：

**阶段驱动的渐进式披露**，而不是完整自适应能力治理系统。

---

## 9. 一句话设计结论

> 通过给 Skill 增加阶段披露配置，并让 orchestrator 按 phase 装配能力，系统可以把“场景配置”升级成“阶段能力治理”，从而减少长任务中的能力噪声、强化阶段边界，并让项目的 runtime 设计更完整。
